# 奇偶チェイン (Parity Chain)

奇数と偶数を交互になぞって、数字の書かれたブロックを消すパズル。Flutter 製。

```
盤面のブロックには数字が書かれていない。色（暖色＝奇数 / 寒色＝偶数）だけ。
数字が書かれているのが目標ブロックで、これを全部消せばステージクリア。

        [7]        ← この目標ブロックを消すには、
                      7 枚以上のチェインに巻き込む必要がある
```

## ルール

- 盤面は 6 × 8。ブロックは **奇数＝暖色 / 偶数＝寒色** で塗り分けられている。
- 上下左右に隣接するブロックを指でなぞって繋ぐ。**連続する 2 枚は必ず偶奇が交互**であること。
- 3 枚以上繋がった状態で指を離すとチェイン成立。**なぞった通常ブロックは全部消える。**
- **数字が書かれているのが目標ブロック。** その数字は「消すのに必要なチェイン長」で、
  ブロックの値ではない。**チェイン長がその数字以上のときだけ消える。**
  足りなければその場に残り、他のブロックだけが消える。
- 目標ブロックを全部消せばステージクリア。**手数を使い切ると失敗。**
- 消えた跡は重力で詰まり、上から新しい通常ブロックが降ってくる。
  **目標ブロックは補充されない**ので、消した分だけ確実に減る。
- 補充されるブロックは **65% が奇数**。奇数同士は繋げないので、偶数は枯れていく側になる。

### 戦略になっているところ

長さ N のチェインは偶奇が交互なので、**必ず偶数を ⌊N/2⌋ 枚消費する**。
補充は奇数に偏っているから、長いチェインほど盤面の偶数を食い潰して次が苦しくなる。

つまり目標ブロックに書かれた数字は、そのまま**希少資源での値段**になっている。
「4」は軽く、「7」は重い。これが手数制限と噛み合って、

**目標を消せる最短の長さで済ませて手数を節約するか、まとめて長く取って一気に片付けるか**

という判断になる。手数制限が無いと「常に最長」が唯一の最適解になり、判断が消える。

目標ブロックが隣り合っていれば、1 本のチェインで複数を巻き込める。
画面上部の偶数ゲージが、そのまま「まだ長いチェインを組めるか」の目安になっている。

## なぜこのルールになったか

2 段階の設計変更を経ている。記録として残しておく。

### 第1段階: 2048 の変種をやめた

当初は 2048 の変種（奇数と偶数がマージできる）として設計していたが、成立性をシミュレーションで
検証した結果、方向を変えた。

| 検証した案 | 結果 |
|---|---|
| 奇数と偶数なら何でも合体（素直な解釈） | **破綻**。奇数+偶数の和は必ず奇数なので偶数が供給されず、平均30手で盤面が奇数だらけになって詰む |
| 上記＋同じ数同士も合体 | **緩すぎ**。AI が一度も負けず、緊張感が消える |
| 偶奇ラダー（1,2,3,4,7,8,15,16,…） | **実質 2048**。目玉の「奇数+偶数」マージは全体の 15.8% に留まり、28% は 2048 と同一の倍加、残りは 1 の端数処理だった |
| 奇数を不安定化して連鎖させる | **爽快感が出ない**。平均 1.18 連、3連以上は 2.0% 止まり |

根本的な原因は、2048 系が「完全一致した 2 枚だけが合体する」ため **1 手あたりの消滅数が構造的に
1 前後に固定される**こと。締めれば連鎖せず、緩めれば緊張感が死ぬ。数字のルールをいじる方向では
抜けられなかった。

そこで消滅条件そのものを変え、**1 回の入力で複数枚が同時に消える**なぞり型にした。

### 第2段階: 合計値の条件をやめ、目標ブロックにした

なぞり型の最初の版は「合計が TARGET 以上なら成立、TARGET は消すほど上がる」というルールだった。
これは動いてはいたが、2 つ問題があった。

- **盤面を見ても難易度が読めない。** 必要合計値という数字は、いま自分がどれくらい苦しいのかを
  伝えてくれない。
- **目的が抽象的。** 「スコアを稼ぎながら詰むまで耐える」以上の目標が無い。

そこで、盤面の大半から数字を外して色だけにし、**数字が書かれた目標ブロックを「消すべきもの」**に
した。数字の意味を「値」から「必要チェイン長」に変えたことで、盤面を見ただけで何をすればいいか、
それがどれくらい重いかが分かるようになった。

合計値が要らなくなったので、ブロックが持つ情報は偶奇の 1 ビットだけになり、データモデルはむしろ
小さくなっている。

#### 検証したこと

**探索コスト。** 新ルールでは「特定のマスを通る長さ N 以上のパスがあるか」を判定する必要がある。
一般には難しい問題だが、深さ上限 8・次数 4・偶奇交互という条件では規模が小さい。
パスを対象マスで 2 本の腕に割る DFS で厳密に判定でき、**存在しないと答える最悪ケースで 750 ノード**
だった（8×6 盤、N=10、奇数率 65%）。しかも偶奇の制約が枝刈りになるので、**盤面が枯れているほど
速く終わる**（奇数率 90% では中央値 2 ノード）。近似も打ち切りも要らない。

**手数の係数。** 目標の周辺を崩して周囲を入れ替える打ち方をする AI で測った。

| 手数 | 目標1個 | 目標3個 | 目標5個 |
|---|---|---|---|
| 目標数 × 2 + 2 | 90% | 79% | 69% |
| **目標数 × 3 + 2** | **93%** | **85%** | **78%** |
| 目標数 × 4 + 2 | 91% | 86% | 79% |

×2+2 は理不尽寄り、×4+2 は緩めた分が間延びになるので、**×3+2** を採った。

**腕の差が出るか。** 同じルールでも、目標から離れた場所を消す AI では必要手数の中央値が 1〜15 手、
p90 が 100 手超という極端な分布になった。目標の周辺を崩す AI に替えると中央値 4〜6 手、p90 が
7〜14 手に収まる。**「目標の周りを崩して周囲のブロックを入れ替える」という学習可能な技術**が
そのまま成績に出る形になっている。

**補充の奇数率。** 合計値の条件が無くなったので、この値の影響は以前より小さい
（0.5 で 90%、0.8 で 84%）。偶奇バーの見た目と手触りを保つため 0.65 を据え置いた。

## 開発

```bash
flutter pub get
flutter test          # ロジック + ドラッグ操作のウィジェットテスト
flutter analyze
flutter run
```

### 構成

| ファイル | 役割 |
|---|---|
| `lib/game/board.dart` | 盤面ロジック。パス判定・部分消去・重力・補充・経路探索。UI 非依存で単体テスト可能 |
| `lib/game/game_controller.dart` | なぞり中の状態、手数、スコア、ステージ進行とクリア／失敗の遷移 |
| `lib/ui/board_view.dart` | なぞり入力と演出（経路の線、弾ける消滅、耐えた目標の揺れ、パーティクル、画面シェイク、触覚フィードバック） |
| `lib/ui/game_screen.dart` | 残り手数・残り目標・偶奇ゲージ、ヒント、クリア／失敗画面 |
| `lib/ui/particles.dart` | パーティクル |
| `lib/ui/theme.dart` | 配色とチェイン称号 |

### 調整できるパラメータ

| 場所 | 意味 |
|---|---|
| `Board.movesFor` | ステージの手数。既定は 目標数 × 3 + 2 |
| `Board.maxRequired` (既定 8) | 目標ブロックに書ける数字の上限。9 以上にすると通るパスが無い盤面が増え、運任せになる |
| `Board.oddChance` (既定 0.65) | 補充時の奇数率。上げるほど偶数が枯れやすく、長いチェインが組みにくくなる |
| `Board.rows` / `cols` (既定 8 × 6) | 盤面サイズ |
| `Board.minPathLength` (既定 3) | チェイン成立に必要な枚数 |
| `GameController.targetCountFor` / `maxRequiredFor` / `moveLimitFor` | ステージごとの難度カーブ |
| `Board.scoreFor` | 得点式。長さの倍率は線形。指数にすると数手で桁が壊れる |

## モバイル向けビルド

アプリ ID は Android / iOS とも `yun.app.chainpuzzle`。ホーム画面での表示名は「奇偶チェイン」。

### アイコン

`assets/icon/` のマスター画像から `flutter_launcher_icons` で各サイズを生成している。
マスターを差し替えたら再生成する。

```bash
dart run flutter_launcher_icons
```

Android のアダプティブアイコンは前景側にセーフゾーン（108dp 中央の 66dp）を作り込んであるため、
`adaptive_icon_foreground_inset: 0` にしてある。前景を描き直すときは、丸マスクで角が切れないか確認すること。

### リリース署名（Android）

`android/key.properties` があれば本番鍵、無ければデバッグ鍵で署名される。
デバッグ鍵の成果物は Play Store に提出できないので、配布前に鍵を用意する。

```bash
keytool -genkey -v -keystore chainpuzzle-upload.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Windows の場合、`keytool` は PATH に入っていない。Android Studio 同梱の JDK にあるので、フルパスで呼ぶ
（PowerShell はパスに空白があるため `&` が要る）。パスは `flutter doctor -v` の "Java binary at" で確認できる。

```powershell
mkdir "$env:USERPROFILE\keystores"
cd "$env:USERPROFILE\keystores"
& "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe" -genkey -v -keystore chainpuzzle-upload.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

対話で聞かれるパスワードと識別名（姓名・組織など）を入力する。パスワードは後で `key.properties` に書くので控えておく。
識別名は空欄のままでも進めるが、証明書に残るので最低限「姓名」は埋めておくとよい。

生成した `.jks` はリポジトリの外（上記なら `%USERPROFILE%\keystores\`）に置き、`android/key.properties.example` を
コピーして `android/key.properties` を作り、パスとパスワードを書く。
**`.properties` ではバックスラッシュがエスケープ扱いになるので、パスは `C:/Users/.../chainpuzzle-upload.jks` と
スラッシュ区切りで書く**（または `\\` に二重化する）。

**この鍵を失うと同じアプリとして更新できなくなる**ので、バックアップを取ること。

```bash
flutter build appbundle --release   # Play Store 提出用 (.aab)
flutter build apk --release         # 直接配布・動作確認用
```

## GitHub Pages への公開

`.github/workflows/deploy-pages.yml` が、デフォルトブランチへのプッシュで自動ビルド・公開する。
公開先は `https://<ユーザー名>.github.io/merge_puzzle/`。

### 初回だけ必要な設定

**リポジトリを public にする**（Settings → General → Danger Zone → Change repository visibility）。

Pages の有効化自体はワークフローの `enablement: true` が行うので、それ以外の設定は不要。

なお、private リポジトリのまま Pages を使うには GitHub Pro 以上が必要になる。
また、どちらの場合でも**公開されたサイトは URL を知っていれば誰でも閲覧できる**
（サイトにアクセス制限をかけられるのは Enterprise Cloud のみ）。

### Flutter web を Pages に載せるときの注意点

| 注意点 | 対処 |
|---|---|
| Pages はリポジトリ名のサブパス (`/merge_puzzle/`) で配信される。既定のビルドはルート配信前提なのでアセットを取りに行けず**真っ白な画面**になる | `--base-href "/merge_puzzle/"` を付ける。ワークフローではリポジトリ名から自動で組み立てている |
| CanvasKit（描画エンジン、約 1.5MB）が既定では Google の CDN から実行時に取得される。CDN が塞がれている環境では起動しない | `--no-web-resources-cdn` でビルドに同梱する |
| 直リンクやリロードで 404 になる | `index.html` を `404.html` に複製する |
| Service Worker が古い版をキャッシュし、更新が反映されないことがある | 利用者側でハードリロード。頻発するなら `--pwa-strategy=none` を検討 |

いずれもワークフロー側で対処済み。ローカルでサブパス配信・CDN 遮断の条件を再現して、起動することを確認している。

なお、日本語とラテン文字のフォントは実行時に Google Fonts から取得される。表示はされるが、
外部依存を完全に断ちたい場合はフォントをアセットとして同梱する必要がある（CJK は容量が大きい）。
