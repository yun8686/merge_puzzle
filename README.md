# 氷炎の鎖 (Frostfire Chain)

熱と冷を交互に継いで鎖を編み、敵の守りを破るパズル。Flutter 製。

```
盤面に敷かれているのはマナ。暖色＝熱の相、寒色＝冷の相。数字は書かれていない。
数字を持つのは敵で、それは「守り」— 上回った分だけがダメージになるしきい値。

        ⬡7        ← 威力 7 で 1 ダメージ、威力 9 なら 3 ダメージ
        ◆◆        ← 体力 2。1本で討つには威力 8 が要る
```

盤面の外には一党が居る。階層をまたいで残るのはこれだけで、盤面は毎回編み直される。

## ルール

- 盤面は 6 × 8。マスには**相**があり、**盤面に出る相は編成した一党で決まる**。
  熱＝暖色、冷＝寒色、雷＝紫。
- 上下左右に隣接するマスを指でなぞって継ぐ。**相の数ぶんの窓の中に、同じ相が
  二度現れてはいけない。** 2相なら「交互」、3相なら「直前2枚と違う相」。
- 3 つ以上継ぐと鎖が成立し、指を離すと発動する。**鎖の長さがそのまま威力**になる。
- **数字を持つのが敵。その数字は「守り」。**
  **ダメージは「威力 − 守り + 1」**。守り以下なら **0 で弾かれ、無傷で残る**。
- 敵は**体力**を持つ。削り切れば討ち取れ、残れば**傷ついたままその場に残る**。
  体力 1 の敵は「守りを上回れば一撃」で、これは体力を入れる前のルールと同じ。
- その階層の敵を全部討てば制圧し、**祝福を1つ選んで**次の階層へ。
- **7階層あるダンジョンを、1階層目から順に降りる。** 最下層を制圧すれば**踏破**。
- **ターンを使い切るか手が尽きると階層を落とす。**
  討ち漏らした敵の**守りの合計だけ一党の体力を失い**、その階層を編み直す。
  体力が尽きたらそのダンジョンは失敗で、**1階層目からやり直し**になる。
- 使ったマナと討った敵の跡は崩れ、上から新しいマナが満ちる。**敵は補充されない。**
- 満ちるマナは **65% が熱の相**。冷の相は湧きが遅く、枯れていく側になる。

### 一党

盤面には置かない。編んだ鎖の戦果にだけ反応する。

| 魔導士 | 能力 |
|---|---|
| 焔の魔導士 | 熱を3枚以上継いだ鎖は威力 +1 |
| 氷雨の魔導士 | 冷を3枚以上継いだ鎖で体力を 1 戻す |
| 雷の魔導士 | **3色を含む8枚以上継いだ**鎖は階層の敵すべてに 1 ダメージ（守りを無視する） |

**誰を連れていくかは潜る前に決める。道中では増えない。** 制圧のたびに選ぶ祝福は
**癒やし / 加護（最大体力+4）** の2択で、増えるのは体力だけ。

### なぜ交互でないと継げないのか

魔力には熱と冷の二相がある。同じ相をいくら重ねても打ち消し合うだけで、流れは生まれない。
熱・冷・熱と交互に継いだときだけ、**継ぎ目に温度差の衝撃が走る**。

この一つの理屈が、ルールの3点を同時に説明する。

| ルール | 理屈 |
|---|---|
| 同じ相は継げない | 継ぎ目ができず、衝撃が生まれない |
| 長い鎖ほど強い | 継ぎ目の数がそのまま威力（長さ N の鎖の継ぎ目は N−1） |
| 守りはしきい値で、弱い一撃は何度でも弾かれる | 衝撃が守りを上回らなければ表面で砕けて通らない |
| 上回った分だけダメージになる | 表面を通った衝撃だけが中に届く |

### 戦略になっているところ

長さ N の鎖は交互なので、**必ず冷の相を ⌊N/2⌋ 枚消費する**。満ちるマナは熱に偏っているから、
強い鎖ほど冷を食い潰して次が苦しくなる。

つまり敵の守りの数字は、そのまま**希少資源での値段**になっている。守り 4 は軽く、7 は重い。
これがターン制限と噛み合って、

**守りを破れる最小の威力で済ませてターンを節約するか、まとめて長く編んで一掃するか**

という判断になる。ターン制限が無いと「常に最長」が唯一の最適解になり、判断が消える。

敵が隣り合っていれば、1 本の鎖で複数を巻き込める。
画面上部の相のバーが、そのまま「まだ強い鎖を編めるか」の目安になっている。

## なぜこのルールになったか

2 段階の設計変更を経ている。記録として残しておく。

### 第1段階: 2048 の変種をやめた

当初は 2048 の変種（奇数と偶数がマージできる）として設計していたが、成立性をシミュレーションで
検証した結果、方向を変えた。

| 検証した案 | 結果 |
|---|---|
| 奇数と偶数なら何でも合体（素直な解釈） | **破綻**。奇数+偶数の和は必ず奇数なので偶数が供給されず、平均30手で盤面が奇数だらけになって詰む |
| 上記＋同じ数同士も合体 | **緩すぎ**。AI が一度も負けず、緊張感が消える |
| 偶奇ラダー（1,2,3,4,7,8,15,16,…） | **実質 2048**。目玉の「奇数+偶数」マージは全体の 15.8% に留まり、28% は 2048 と同一の倍加、残りは 1 の端数処理だった |
| 奇数を不安定化して連鎖させる | **爽快感が出ない**。平均 1.18 連、3連以上は 2.0% 止まり |

根本的な原因は、2048 系が「完全一致した 2 枚だけが合体する」ため **1 手あたりの消滅数が構造的に
1 前後に固定される**こと。締めれば連鎖せず、緩めれば緊張感が死ぬ。数字のルールをいじる方向では
抜けられなかった。

そこで消滅条件そのものを変え、**1 回の入力で複数枚が同時に消える**なぞり型にした。

### 第2段階: 合計値の条件をやめ、目標ブロックにした

なぞり型の最初の版は「合計が TARGET 以上なら成立、TARGET は消すほど上がる」というルールだった。
これは動いてはいたが、2 つ問題があった。

- **盤面を見ても難易度が読めない。** 必要合計値という数字は、いま自分がどれくらい苦しいのかを
  伝えてくれない。
- **目的が抽象的。** 「スコアを稼ぎながら詰むまで耐える」以上の目標が無い。

そこで、盤面の大半から数字を外して色だけにし、**数字が書かれた目標ブロックを「消すべきもの」**に
した。数字の意味を「値」から「必要チェイン長」に変えたことで、盤面を見ただけで何をすればいいか、
それがどれくらい重いかが分かるようになった。

合計値が要らなくなったので、ブロックが持つ情報は偶奇の 1 ビットだけになり、データモデルはむしろ
小さくなっている。

#### 検証したこと

**探索コスト。** 新ルールでは「特定のマスを通る長さ N 以上のパスがあるか」を判定する必要がある。
一般には難しい問題だが、深さ上限 8・次数 4・偶奇交互という条件では規模が小さい。
パスを対象マスで 2 本の腕に割る DFS で厳密に判定でき、**存在しないと答える最悪ケースで 750 ノード**
だった（8×6 盤、N=10、奇数率 65%）。しかも偶奇の制約が枝刈りになるので、**盤面が枯れているほど
速く終わる**（奇数率 90% では中央値 2 ノード）。近似も打ち切りも要らない。

**手数の係数。** 目標の周辺を崩して周囲を入れ替える打ち方をする AI で測った。

| 手数 | 目標1個 | 目標3個 | 目標5個 |
|---|---|---|---|
| 目標数 × 2 + 2 | 90% | 79% | 69% |
| **目標数 × 3 + 2** | **93%** | **85%** | **78%** |
| 目標数 × 4 + 2 | 91% | 86% | 79% |

×2+2 は理不尽寄り、×4+2 は緩めた分が間延びになるので、**×3+2** を採った。

**腕の差が出るか。** 同じルールでも、目標から離れた場所を消す AI では必要手数の中央値が 1〜15 手、
p90 が 100 手超という極端な分布になった。目標の周辺を崩す AI に替えると中央値 4〜6 手、p90 が
7〜14 手に収まる。**「目標の周りを崩して周囲のブロックを入れ替える」という学習可能な技術**が
そのまま成績に出る形になっている。

**補充の奇数率。** 合計値の条件が無くなったので、この値の影響は以前より小さい
（0.5 で 90%、0.8 で 84%）。偶奇バーの見た目と手触りを保つため 0.65 を据え置いた。

### 第3段階: 世界観を載せた

ルールは変えずに、呼び名と見た目だけをファンタジーに寄せた。対応は素直に付いた。

| 実装 | 世界観 |
|---|---|
| 目標ブロックのしきい値 | 敵の守り |
| チェインの長さ | 鎖の威力 |
| 偶奇が交互 | 熱と冷を交互に継ぐ |
| 長いチェインが偶数を食う | 強い鎖ほど冷の相を食い潰す |
| 長さ不足で消えずに残る | 守りに弾かれて無傷 |
| 手数 / ステージ | ターン / 階層 |

ここで一点だけ設計判断がある。最初は炎と氷の**属性**にしようとしたが、炎と炎を継げない理由が
出てこない（普通は大きい炎になる）。属性は並列であって対立項ではないためで、偶奇が納得される
のは偶奇が数学的に排他だからだ、という点を踏まえて**相**にした。熱と冷なら「同相では流れが
生まれない」で交互性が要請され、しかも**継ぎ目の数＝威力**で長さの意味まで同じ理屈から出る。
色は炎と氷のまま残し、呼び名だけを相に変えてある。

実装側（`board.dart` / `game_controller.dart`）は偶奇のまま一行も触っていない。世界観は
`theme.dart` と UI の文言だけに載っているので、検証済みの数値はそのまま生きている。

### 第4段階: 体力と一党を足した

ここで初めて、世界観がルールを増やした。敵に**体力**を、盤面の外に**一党**を置いた。

#### HP 制だけを入れると、ゲームが壊れる

最初の案は「連結数がそのまま敵の HP を削る」だった。これは**採らなかった**。

守り 8 の敵に対して、最小の 3 連を 3 回撃てば 9 ダメージで落ちる。敵1体の階層には
5 ターンあるので**常に足りる**。しかも 3 連が食う冷の相は 1 枚、8 連なら 4 枚。
第2段階で作った**「強い鎖ほど冷を食い潰して次が苦しくなる」という希少資源のジレンマが、
最小連打で丸ごと回避できてしまう**。「破れる最小の威力で済ませるか、まとめて長く編むか」
という判断が消えて、答えが「常に最小」の一択になる。

そこで**守りを防御力として残した**。

```
ダメージ = 威力 − 守り + 1   （守り以下なら 0）
```

守り未満の鎖は**何度撃っても 0** なので、最小連打は成立しない。上回った分だけが通るので、
長く編む意味も残る。そして体力 1 の敵は「守りを上回れば一撃」のままなので、
**第2段階までのルールはこの式の特殊形として丸ごと残っている**（`board_test.dart` に
その同値性を確かめるテストを置いてある）。

体力が足す軸は「1本の鎖の長さ」ではなく**ターン数**で、これは長さに還元されない。
これまで盤面上のすべてが「1本の鎖の長さ」に潰れていたので、ここが新しい判断になる。

#### 一党は盤面に触らない

魔導士は盤面に置かず、編んだ鎖の戦果（枚数・熱の枚数・冷の枚数）だけを見て反応する。
`party.dart` は `board.dart` を読まないので、検証済みのパズルの数値はここでも生きている。

能力の条件に「熱を3枚以上」を選んだのには理由がある。交互ルールのせいで、長さ N の鎖に
含まれる熱は**熱から始めれば ⌈N/2⌉、冷から始めれば ⌊N/2⌋**に決まる。つまりこの条件は
実質「長さ＋**どちらの相から始めたか**」で、**開始する相の選択に初めて意味が生まれる**。
これまで開始相は繋がりやすさ以外どうでもよかった。

#### 体力を、階層をまたぐ唯一の資源にした

ターン切れは即ゲームオーバーではなくなり、**討ち漏らした敵の守りの合計だけ一党の体力を
失って、その階層を編み直す**ようにした。弾かれ損のストレスを、しきい値の意味を壊さずに
吸収できる。初期体力 30 は、守り 5 の敵を2体残せば 10 なので、2〜4回の取りこぼしに耐える
計算。README のクリア率（階層あたり 78〜93%）と噛み合って、じわじわ削られていく。

#### 雷が落ちたことを見せる

雷の追撃は**鎖の外**で起きる。守りを無視して階層の敵すべてを削るので、なぞった場所とも
鎖の色とも関係がない。ここに演出を付けないと、盤面の離れた場所で敵が消えたり体力だけ
減ったりして、何が起きたのか分からない。

そこで盤面の上端から、当たった敵1体につき1本ずつ雷を落とす。鎖の色（熱／冷）ではなく
魔導士の金で描き、盤面ごと金に光らせて「鎖とは別の理屈で起きたこと」にしてある。

条件は**威力ではなく継いだ枚数**にしてある（`stormChain`、8枚）。焔の補正が乗ると 7 枚でも
威力 8 になるが、それでは落とさない。「8枚つなぐ」は盤面を見ながら数えられるのに対し、
「威力 8」は補正が乗るかどうかを頭の中で足さないと分からず、狙って出せないため。
魔導士の能力で唯一、ここだけが枚数を見ている。

落とす先は**討ち取れなかった敵も含めた全部**。討った敵しか光らせないと、体力だけ削られた
敵に何が起きたのか見えない。`ClearResult.bolt` は討ち取れた敵しか持たないので、演出用に
当たったマスを `boltCells` として別に持たせている。

討たれた敵は、弾けている間もマスに居たときと同じ姿のまま膨らんで消える。数字だけを残すと
「敵が消えて数字が残った」ように見えて、討ち取った相手が分からない。盤面から敵が居なくなる
のは、演出が終わったときになる。

#### 検証していないこと

**手数の係数を、体力の合計で数え直した**（`Board.movesFor` の引数が体数から体力の合計に
変わった）。体力 1 の敵しか居ない階層では以前と完全に同じ値になるので、第2段階の
シミュレーション結果はそのまま効いている。一方、**体力 2〜3 の敵が混ざる階層の ×3+2 は
外挿であって、測っていない**。1体を討つのに必要な「周辺を崩して入れ替える」手間は
殴るたびに払うので 1ヒットあたり 3 手という読みだが、深い階層の尺が伸びすぎるようなら
ここが最初の調整先になる。

### 第5段階: ダンジョン制にした

無限に潜る形をやめ、**7階層のダンジョンを順に踏破する**形に変えた。ルールは一行も
変えていない。変えたのは階層の並べ方と、一党がいつ決まるかの2点。

#### 階層を手で書くようにした

それまでは階層番号から敵の数・守りの上限・体力の上限を計算していた（`foeCountFor` など）。
自動生成では「B3F で初めて2回殴らされる」「B6F で手数が足りなくなる」といった段取りを
作れない。決め打ちのダンジョンでは、そこが遊びの骨になる。

そこで階層は `dungeon.dart` に手で書き、`Board.buildStage` に敵の一覧を渡す形にした。
散らす側（`foeCount` を渡す方）は消していない。無限に潜る遊び方を足したくなったら
そのまま使える。

手で書く側には**「守りが厚い敵ほど体力は薄く」という縛りを掛けていない**。散らす側には
掛けてある（厚い守りと厚い体力が重なると、1本で討てないうえに削るのにも何ターンもかかる、
ただ長引くだけの敵になる）。これを破ってよいのは最下層の主だけ、という判断は書く側の責任
にした。

#### 一党を潜る前に決めるようにした

制圧の祝福から「同行」を外し、誰を連れていくかは潜る前に固定した。道中で増えると、
**編成が判断にならない**。「引けた顔ぶれで、このダンジョンをどう攻めるか」を考えさせたい
のに、道中で勝手に揃ってしまうと考える余地が消える。

祝福は癒やし・加護の2択になり、階層をまたいで増えるのは体力だけになった。

#### ダンジョンは3本

| ダンジョン | 性格 |
|---|---|
| 忘れられた坑道 | 守りが薄い。B3F で初めて体力2の敵に当たる |
| 凍てついた回廊 | 体力が厚い。殴る回数＝ターンを要求する |
| 竜の巣 | 守りが厚い。1本の鎖に要る枚数が大きい |

要求するものを変えてあるのは、**編成の選択に意味を持たせるため**。どのダンジョンも同じ
強さを求めるなら、強い3人を入れるだけになって編成が判断にならない。

#### 検証していないこと

**手で書いた階層の難度は測っていない。** 第2段階のシミュレーション（AI にプレイさせて
クリア率を出す）のコードはリポジトリに残っておらず、今回は測り直していない。手数は
体力の合計 × 3 + 2 という既存の式をそのまま使っているが、この係数は体力1の敵しか
居ない盤面で測った値なので、体力2〜3が混ざる階層では外挿のままになっている。

詰まる階層が出たら、まず `FloorSpec.moves` でその階層だけ手数を上書きするのが最小の手当て。

### 第6段階: 拠点・編成・ガチャ

ダンジョン制にしたことで、**潜る前と潜ったあと**が要るようになった。そこを拠点にまとめた。

```
拠点 ─ 魔晶 / ガチャ / 一党の編成 / ダンジョン選択
  └ 潜る ─ 7階層 ─ 踏破 or 全滅 ─ 拠点へ戻る（魔晶が入る）
```

#### 拠点は三つの面に分けた

縦に全部並べると「いま何ができるか」が埋もれるうえ、いちばん押すダンジョンまで毎回
スクロールすることになる。下のタブで **ダンジョン / 一党 / ガチャ** を行き来する形にした。
上の帯（名乗りと魔晶）はどの面でも出したままにしてある。

ダンジョンの札には**その最下層の主**を薄く敷いてある。盤面で戦う相手の姿がそのまま
出るので、名前だけより「どこへ行くのか」が伝わる。`foe_art.dart` の姿を盤面の外でも
使い回しているだけで、絵は増えていない。

挑む前に誰を連れていくかが見えていないと、選び直しに戻る羽目になるので、ダンジョンの
面の下端に一党の帯を置いた。押すと編成の面に移る。

#### 記録は拠点だけが持つ

所持している魔導士・踏破したダンジョン・魔晶・編成は `progress.dart` にまとめ、
保存は `shared_preferences`（web では localStorage）。**盤面の画面は記録を知らない。**
潜るときは「どのダンジョンを、誰を連れて」だけを渡し、帰るときは踏破したか・どこまで
降りたかだけを返す。魔晶を足して書くのは拠点の仕事で、盤面の側には一行も無い。

保存は**読み書きに失敗しても投げない**。壊れた保存も黙って捨てて、まっさらな記録として
扱う。プライベートウィンドウや保存を塞いだブラウザで、保存が効かないだけなら遊べる。

#### 魔導士は7人・枠は3

| 魔導士 | 能力 |
|---|---|
| 焔 | 熱を3枚以上継いだ鎖は威力 +1 |
| 烈火 | 熱を5枚以上継いだ鎖は威力 +2 |
| 氷雨 | 冷を3枚以上継いだ鎖で体力を 1 戻す |
| 霜 | 冷から継ぎ始めた鎖は威力 +1 |
| 雷 | 3色を含む8枚以上継いだ鎖は階層の敵すべてに 1 ダメージ |
| 風 | 7枚以上継いだ鎖はターンを 1 返す |
| 盾 | 階層を落としたときの痛手が半分になる |

全員「鎖の戦果だけを見る」制約の中に収めてある。霜のために `ChainTally` に**開始した相**を
足した。交互ルールのせいで開始相だけで熱冷の枚数が1枚ずれるので、枚数とは別に要る。

焔と烈火は重なって乗るので、熱を5枚継げば +3。霜は開始相だけを見るので熱に寄せる
編み方とは噛み合わない。**「熱を長く継ぐ」か「冷から始める」かで育て方が割れる**。

風の 7枚 は冷の相を3枚食う長さ。ここを下げると、長い鎖を編めるうちはターンが減らなく
なって階層の制限が意味を失う。枯渇そのものが歯止めになる位置に置いてある。

#### ガチャは未所持からしか引かない

名簿が7人しか居ないので、重複を出すと「何も増えない引き」ばかりになる。実質は
**ランダムな解放順**で、引き直す動機は続かない。ロースターを増やすまでは、これ以上の
仕掛けを載せても空回りする。1回 10 魔晶で、初回踏破 +10 / 2回目以降 +3 /
失敗しても到達階層ぶんは持ち帰る。

#### 検証していないこと

**魔晶の値段も、増えた魔導士の強さも測っていない。** 風は実質ターン消費ゼロを作れるし、
烈火と焔を重ねた +3 は守りの厚いダンジョンを軽くする。どこかが壊れていてもおかしくない。

### 第7段階: 相を編成で決めるようにした

熱と冷の2相固定をやめ、**盤面に出る相を編成した一党で決める**ようにした。
魔導士はそれぞれ相を1つ持ち、連れていった相だけがマナとして敷かれる。

#### 素直な一般化は、パズルを壊す

「隣り合う2枚が違う相なら継げる」とそのまま広げると、こうなる（6×8 盤、300回）。

| 盤面 | 最長の中央値 | 8枚以上編める | 12枚まで届く |
|---|---|---|---|
| 2相 65:35（それまでの盤面） | 11 | 89% | **48%** |
| 3相・隣と違えばよい | 12 | 100% | **100%** |

相が増えるほど繋ぎ先が増えるので、**ほぼ全部の盤面で12枚編めてしまう**。雷の
「8枚以上」は常に満たせ、第2段階の芯だった「強い鎖ほど希少な相を食い潰して
次が苦しくなる」というジレンマが消える。

#### N 枚ぶんの窓に、同じ相は二度出ない

代わりにこうした。**相が N 個あるなら、N 枚ぶんの窓の中に同じ相が二度現れては
いけない。** 2相なら「直前1枚と違う」＝交互で、**それまでの規則と完全に同じ**。
3相なら「直前2枚と違う相」になる。

| 盤面・規則 | 最長の中央値 | 8枚以上 | 12枚まで |
|---|---|---|---|
| 2相 65:35（それまで） | 11 | 89% | 48% |
| 3相・隣と違えばよい | 12 | 100% | 100% |
| **3相・直前2枚と違う** | **9** | **77%** | **24%** |
| 3相・決まった順に循環 | 10 | 79% | 26% |
| 3相・補充が 2:1:1・直前2枚と違う | 8 | 62% | 14% |

それまでの手応えとほぼ同じ場所に着地する。決まった順に循環させる案も同じくらい
だったが、2相のときの規則と地続きにならないので採らなかった。

#### 補充の比率は編成の人数比

同じ相の魔導士を重ねると、その相が多く降ってくる。**2:1 なら 67:33 で、偶奇
だった頃の 65:35 とほぼ同じ**。少ない側の相が「強い鎖を編むのに要る希少な資源」
になるので、第2段階のジレンマがそのまま残る。

#### 相は2種類以上

**1相だけの編成は組めない。** 同じ相は続けて継げないので、1色の盤面では鎖が
1枚も編めず、入った瞬間に手詰まりになる。枠の数でも人数でもなく、ここだけが
編成の縛りになっている。外すと1色になる魔導士は編成から外せない。

始まりの3人は**相を1つずつ持つだけの従者**で、特殊な力を持たない。招ける7人は
それぞれ相を持ち、能力は「**自分の相**を N 枚以上」という形に読み替えた。誰を
入れると盤面が何色になるかが、編成の画面で色だけで読める。

**持っているのは従者3人だが、始まりの編成は2人**（熱と冷）。3枠を最初から埋めて
しまうと、初めて引いた魔導士が編成に入らず、誰かを外すところから始めることに
なる。1枠空けておけば引いた人がそのまま入り、次の潜りで違いが出る。空けるのは
雷の枠で、熱と冷の2相なら継ぎ方は「直前1枚と違う」＝交互、いちばん編みやすい
盤面から始まる。

#### 能力は「条件と効き目の組」で書く

魔導士を足すたびに `Party` の中の分岐が増える作りだった。焔が居れば威力に +1、
風が居ればターンを 1 返す、というのを1人ぶんずつ手で書いていたので、**1人足す
のに 5 箇所直す**ことになる。説明文も手書きで、定数を動かすと文だけ古くなった。

能力をデータにした。**条件（`Trigger`）と効き目（`Boon`）の組**でしか書けない。

```dart
static const ember = Mage._(MageKind.ember, Phase.heat, '焔の魔導士', '焔',
    Ability(SamePhase(emberSame), PowerUp(1)));
```

`Party` は「応えた `PowerUp` を全部足す」としか書いていない。誰が居るかでは
分岐しないので、**名簿に何人足しても `Party` は変わらない**。魔導士を1人足す
のに触るのは `MageKind` と名簿の2箇所だけになった。

説明文も組から作る（「熱を3枚以上継いだ鎖」＋「は威力 +1」）。
手で書いた文と数値がずれることが無い。

条件は4つ（自分の相を N 枚・鎖が N 枚・自分の相から始まる・常に）、効き目は
5つ（威力・ターン・回復・全体攻撃・被害軽減）。**組で書けない能力を足したく
なったら、`Party` に `if` を書かずに条件か効き目を1つ増やす。** そこを崩すと
また魔導士ごとの分岐に戻る。

#### 3色にする理由を雷に持たせた

相を編成で決められるようにしたあと、**3色にする理由がどこにも無かった**。

3色は継ぎ先が薄くなるぶん、鎖が短くなる（最長の中央値 9・8枚以上 77%。2色なら
11・89%）。相の枚数を見る能力（焔・烈火・氷雨）も、1相あたりの取り分が
50% から 33% に落ちるぶん発動しにくい。相を見ない能力（風・雷・盾）は3色にしても
得をしない。つまり3色は**払うだけで何も返ってこない**選択だった。

そこでいちばん派手な能力を3色に結んだ。**雷は3色の盤面でしか落ちない。**

短くなった盤面で 8 枚を編むのは、2色で 8 枚を編むより明確に難しい（77% 対 89%）。
「3色にしてでも 8 枚を狙う」が編成の判断になり、2色は「編みやすさを取る」という
別の答えになる。雷を2色の編成に入れても一度も落ちないので、そこは編成の画面で
色を見て避けてもらう。

条件は `Every([DistinctPhases(3), ChainLength(8)])` と書いてある。「鎖が3種類の
相を含む」は、継ぎ方の決まりのおかげで**「盤面が3色である」とほぼ同じ意味**になる。
3色の盤面では長さ3以上の鎖は必ず3色を含み、2色の盤面ではどう編んでも3色にならない。
盤面を見に行かずに鎖の戦果だけで書けるので、`party.dart` が `board.dart` を
読まない約束もそのまま残る。

#### 相が2つだった頃の理屈はどうなったか

第3段階では「炎と炎を継げない理由が出てこない。偶奇が納得されるのは偶奇が
数学的に排他だからだ」として**属性ではなく相**にした。3つ以上になると排他性の
説明は使えない。

代わりに残ったのは**「継ぎ目に差が要る」**という方の理屈で、こちらは相がいくつ
あっても成り立つ。同じ相が近すぎると打ち消し合い、衝撃が積み上がらない。
2相のときはそれが「交互」という形で現れていただけだった。

#### 検証していないこと

**上の数字は「編めるかどうか」しか測っていない。** クリア率も手数の係数も
測り直していないので、3色のダンジョンが実際に易しいのか難しいのかは分からない。
守りの上限8や手数の×3+2は2相のときの値のまま置いてある。

**敵は相を持たない。** 弱点を突くような仕掛けを足すなら、そこが次の一手になる。

### 第8段階: 3色の盤面を編めるようにした

遊んでみると、3色の盤面は目に見えて詰まる。第7段階では「盤面のどこかに長い鎖が
あるか」しか測っていなかったが、実際に効くのは**敵マスを通る鎖の長さ**だった。
敵を討つには敵マスを通る鎖が要り、その威力は枚数で決まる。

#### 測り方を変えた

まず「継げる隣マスの割合」で測ったが、これは当てにならなかった。3色・巡回では
次に置ける相が常に1種類（盤面の 1/3）で、2色盤の1種類（盤面の 1/2）より薄い。
そこから「2色に絞っても次は1種類のままだから効かない」と読んだが、**間違い
だった**。

正しくは**ランダムに置いた敵1体のマスを通る最長パス**で測る。敵を討つには敵マスを
通る鎖が要り、威力は枚数で決まるので、これがそのまま「その敵にどれだけ通せるか」
になる。

通常盤面 8×6＝48マス・上下左右のみ・相は均等・2000面で1回ぶん、種を変えて5回。
**12枚で打ち切る**（守りの上限は8で、威力9あればどの敵も討てる。それ以上の長さは
ゲームの上で差にならない）。`python3 tools/sim/chain_length.py` で出せる。

| 3色盤面の決まり | 敵マスを通る最長パス | 3枚以上 | 5枚以上 | 8枚以上 |
|---|---|---|---|---|
| （基準）2相・交互 | **7.43** ± 0.08 | 83% | 68% | 51% |
| 巡回のみ（第7段階） | 6.06 ± 0.08 | 85% | 63% | 31% |
| **2色の交互 or 3色の巡回** | **7.42** ± 0.08 | 95% | 83% | 47% |
| どの4枚にも3色 | 10.56 ± 0.12 | 95% | 90% | 85% |
| 隣と違えばよい | 11.16 ± 0.09 | 95% | 93% | 91% |

1手ぶんの確率では捉えられない差がここに出る。**選べること自体が長さを押し上げる**
ので、どちらのモードも局所的には1種類しか置けなくても、良い方を取れる鎖は長い。

#### 決まりは2本立てにした

**鎖ごとにどちらかを選ぶ。**

  - **2色の交互** … 使う相が2つだけなら、隣り合う2枚が違えばよい
  - **3色の巡回** … 3色目を踏んだら、直前2枚と同じ相は継げない

3枚目で1枚目の相に戻れば前者に確定し、以降その2色だけ。3色目を踏めば後者で、
以降は巡回しか編めない。**戻ったあとに3色目を継ぐことはできない**（巡回に
切り替わると、戻った3枚目が後から無効になるため）。

7.42 枚で、2色だった頃の 7.43 枚と一致する（振れ幅 ±0.08 の中）。**短い鎖で
詰まることはむしろ減っていて**、3枚すら編めない敵が 17% から 5% に、5枚届かない
敵が 32% から 17% に落ちる。長い鎖（8枚以上）だけが 51% → 47% と少し薄い。

**2色の編成では第7段階までと完全に同じ決まり**になる。相が2つなら「使う相が
2つだけ」が常に成り立つので、条件として何も足していない。

雷の「3色を含む」は意味が変わった。以前は3色盤の4枚以上の鎖が必ず3色を含んだが、
いまは**2色の鎖を選べば3色にならない**。長く編んで威力を取るか、巡回で編んで雷を
落とすかが、鎖1本ごとの判断になる。

緩めすぎの案は採らなかった。「どの4枚にも3色」で 10.56 枚、「隣と違えばよい」で
11.16 枚。どちらも2色だった頃を大きく超え、第2段階の芯だった希少な相のジレンマが
消える。

#### 決まりが並び全体の性質になった

第7段階までは「窓の中を見る」だけで済んだので、鎖の端だけ見れば継げるかどうかが
決まった。いまは**2色で往復してきた鎖に3色目を継ぐと、それまでの往復が後から
無効になる**。端だけでは足りないので、`_fits` は毎回並びを組み直して
`_chainFits` に渡す。

前から見ても後ろから見ても同じ決まりであることは変わらない（「使う相が2つだけ」も
「窓の中に同じ相が二度出ない」も、並びを裏返しても変わらない）ので、鎖を両端から
伸ばす `findPathThrough` はそのまま動く。

#### 検証していないこと

クリア率も手数の係数も測り直していない。守りの上限8や手数の×3+2は2相のときの
値のまま置いてある。

### 第9段階: 敵が毎ターン殴ってくるようにした

体力が減るのは階層を落としたときだけだった。1階層につき最大1回しか痛手が無い
ので、**敵が居ることの圧が手の中に無い**。盤面を眺めて最善手を探しているあいだ、
失うものが何も無かった。

**残っている敵が毎ターン殴ってくる。** 1手ごとに、生きている敵の攻撃力の合計だけ
体力が減る。討ち取れば減るので、**早く討つほど後が楽**になる。

制圧した手だけは殴られない。最後の1体を討った瞬間に反撃が来ると、制圧したのに
体力が減るという腑に落ちない目に遭う。

#### 攻撃力は隠す

攻撃力はマスに出さない。マスに出ているのは守りだけで、これは鎖の長さを決める
唯一の値だから見せている。40〜50px のマスに数字を2つ並べると、どちらも読めなく
なる。

守りの厚さから決まる（`Board.attackFor`）。守り3〜5が1、6〜8が2。**厚い敵ほど
痛い**という対応さえ付いていれば、数字を見せなくても体力バーの減り方で伝わる。

手で上書きもできる（`FoeSpec(6, atk: 4)`）。守りは薄いのに殴りだけ痛い敵を
置きたくなったときのため。

#### 体力は30から120へ

階層あたりの痛手が「攻撃力の合計 × その階層に使った手数」になるので、桁が変わる。
いまのダンジョン定義で見積もるとこうなる（手数の6割で制圧、敵は順に落ちるので
平均して半分が生きている、という勘定）。

| ダンジョン | 1本を通して浴びる見込み |
|---|---|
| 忘れられた坑道 | 68 |
| 凍てついた回廊 | 106 |
| 竜の巣 | 181 |

体力 120 で始め、階層のあいだの祝福（癒やしは最大体力の4割＝48）で足していく。
坑道は素で通る。竜の巣は癒やしを2回は選ばないと届かない——**祝福の選択が初めて
判断になる**。

氷雨の回復も 1 では焼け石に水なので 3 にした（`rimeMend`）。毎ターンの反撃が
2〜6 なので、条件を満たした手では半分ほど打ち消す。全部打ち消すと敵を放置して
延々と編めてしまい、討ち急ぐ理由が消える。

#### 盾は「受ける痛手」全体に効かせた

盾は「階層を落としたときの痛手が半分」だった。痛手の大半が毎ターンの反撃に移った
ので、そのままだとほとんど死に札になる。**受ける痛手すべてを半分**にした
（`Party.damageFor`）。説明文は能力の組から作られるので、文も自動で変わる。

#### 向きが無いと、殴ったのがどちらか分からない

演出を「どこで鳴らすか」は、意味を決めてしまう。**その場所が痛手を受けた、という
意味になる。** 敵の上で弾けさせると、こちらが敵を攻撃したように見える。

当たる時刻は `Timer` で決めてある（`_windUp` + `_travel`）。線が届いたという
描画側のコールバックに任せると、ウィジェットが途中で消えたときに反撃が起きないまま
入力も止まったままになる。**線はただ絵として乗せる。**

#### 殴られるまでに一拍置く

最初は `settle`（盤面を詰める）と同時に殴っていた。消した瞬間に反撃が始まるので、
**自分の手と相手の手が重なって読めない**。何が起きて体力が減ったのか分からない。

`settle` は盤面を詰めて `isStriking` を立てるだけにして、痛手を出すのは `strike`
に分けた。詰んだ盤面を一拍（420ms）見せてから殴る。制圧したときの `_clearPause`
（300ms）より少し長いのは、こちらは敵の動きがそのあとに続くため。

この間は `acceptsInput` が false。殴られる前に次の手を打たれると、反撃が起きた順が
分からなくなる。

#### 殴られたことを、盤面を見たまま知らせる

一党の帯に `-N` を出すだけでは足りなかった。**目は盤面にある**。毎ターン殴られる
以上、視線を動かさずに分かる知らせが要る。

演出は3つ重ねてある。**どれか1つでは足りなかった。**

**1. 殴った敵そのもの。** 残っている敵が1体ずつ振りかぶって打ち込み、そこから
盤面の下端――一党の帯がある側――へ赤い一撃が飛ぶ。何体居ても一撃は1点に集まるので、
狙われているのが誰なのかが読める。画面全体を赤くするだけでは**誰に殴られたのか**が
分からない。

最初は敵の上で赤い爪痕と飛沫を弾けさせていたが、**こちらが敵を攻撃したように
見えてしまった**。爆発も衝撃波も、その場所が「殴られた」ことを意味する。敵の上で
鳴らしてよいのは**向きのある動きと線だけ**で、弾けるのは一党の側。

動きも「いきなり突き出す」では駄目で、突き飛ばされたようにも見える。**いったん
引いてから踏み込む**と、動きを起こしたのが敵の側だと読める。

**2. 盤面ごと赤に振って揺らす。** 鎖の演出は相の色（暖色・寒色・紫）なので、赤は
必ず「殴られた」を指す。枠の発光も赤に寄せる。

**3. 画面の縁から赤が差す**（`_HurtFlash`）。**中央は透かしたまま**にしてあるのが
肝で、盤面の上に色を乗せるとマスの相が読めなくなり、次の手が選べない。立ち上がり
は速く（全体の 10%）、引くのはゆっくり。700ms で消える。立ち上がりの一瞬だけは
画面全体も薄く沈める——縁だけだと目の端に流れてしまう。

濃さは受けた量で変わるが頭打ちにしてある。毎ターンの反撃は 1〜6、階層を落とした
ときの反撃は 20 を超えるので、そのまま比例させると画面が真っ赤に潰れる。

帯の `-N` も1手ごとに跳ね直す。出しっぱなしの文字だと、同じ量が続いたときに
「まだ殴られているのか、さっきのが残っているのか」が分からない。

走らせるきっかけは**量ではなく回数**（`GameController.hitTick`）。量だけを見て
いると、同じ痛手が続けて来たときに値が変わらず、2回目の演出が鳴らない。

#### 検証していないこと

クリア率を測り直していない。上の見込みは机上の勘定で、実際に何ターンで制圧できる
かは遊んでみないと分からない。`Board.attackFor` と `Party.startingHp` は対で
動かすこと。

### タイトル画面

**遊び方は書かない。鎖が編まれるところを見せる。** 題の上で 熱→冷→雷→熱→冷 と
マスが順に灯り、線で繋がっていく。押す前に「色を継いで繋げる遊びだ」が伝わるし、
並びを実際に編める形（同じ相が続かない）にしてあるので、決まりまで絵で読める。

題は日本語なので既定の書体で組み、色だけ相のグラデ（熱→冷）で塗った。見出しの
書体 Baloo2 には日本語が入っていないので、そちらは下のラテン字に回している。

**記録を読まない。** 押されたら拠点に渡すだけ。ここが保存の都合を持つと、タイトル
を出すのに読み込みを待つことになる。

**Navigator で積まない**（`main.dart` の `_Entry`）。タイトルへ戻る道は無いので、
積むと端末の「戻る」で拠点が消えてタイトルに落ちる。入れ替えなら戻り道は生まれない。

鎖の絵と始める口の脈は `repeat` で回っている。テストで `pumpAndSettle` を使うと
止まらないまま待ち続けるので、タイトルを含むテストは `pump(Duration)` で送る。

## モバイル向けビルド

アプリ ID は Android / iOS とも `yun.app.chainpuzzle`。ホーム画面での表示名は「氷炎の鎖」。

Dart のパッケージ名は `parity_chain` のまま。内部識別子で、import 文が全部これを指している。

### アイコン

`assets/icon/` のマスター画像から `flutter_launcher_icons` で各サイズを生成している。
マスターを差し替えたら再生成する。

```bash
dart run flutter_launcher_icons
```

Android のアダプティブアイコンは前景側にセーフゾーン（108dp 中央の 66dp）を作り込んであるため、
`adaptive_icon_foreground_inset: 0` にしてある。前景を描き直すときは、丸マスクで角が切れないか確認すること。

### リリース署名（Android）

`android/key.properties` があれば本番鍵、無ければデバッグ鍵で署名される。
デバッグ鍵の成果物は Play Store に提出できないので、配布前に鍵を用意する。

```bash
keytool -genkey -v -keystore chainpuzzle-upload.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Windows の場合、`keytool` は PATH に入っていない。Android Studio 同梱の JDK にあるので、フルパスで呼ぶ
（PowerShell はパスに空白があるため `&` が要る）。パスは `flutter doctor -v` の "Java binary at" で確認できる。

```powershell
mkdir "$env:USERPROFILE\keystores"
cd "$env:USERPROFILE\keystores"
& "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe" -genkey -v -keystore chainpuzzle-upload.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

対話で聞かれるパスワードと識別名（姓名・組織など）を入力する。パスワードは後で `key.properties` に書くので控えておく。
識別名は空欄のままでも進めるが、証明書に残るので最低限「姓名」は埋めておくとよい。

生成した `.jks` はリポジトリの外（上記なら `%USERPROFILE%\keystores\`）に置き、`android/key.properties.example` を
コピーして `android/key.properties` を作り、パスとパスワードを書く。
**`.properties` ではバックスラッシュがエスケープ扱いになるので、パスは `C:/Users/.../chainpuzzle-upload.jks` と
スラッシュ区切りで書く**（または `\\` に二重化する）。

**この鍵を失うと同じアプリとして更新できなくなる**ので、バックアップを取ること。

```bash
flutter build appbundle --release   # Play Store 提出用 (.aab)
flutter build apk --release         # 直接配布・動作確認用
```

## GitHub Pages への公開

`.github/workflows/deploy-pages.yml` が、デフォルトブランチへのプッシュで自動ビルド・公開する。
公開先は `https://<ユーザー名>.github.io/merge_puzzle/`。

### 初回だけ必要な設定

**リポジトリを public にする**（Settings → General → Danger Zone → Change repository visibility）。

Pages の有効化自体はワークフローの `enablement: true` が行うので、それ以外の設定は不要。

なお、private リポジトリのまま Pages を使うには GitHub Pro 以上が必要になる。
また、どちらの場合でも**公開されたサイトは URL を知っていれば誰でも閲覧できる**
（サイトにアクセス制限をかけられるのは Enterprise Cloud のみ）。

### Flutter web を Pages に載せるときの注意点

| 注意点 | 対処 |
|---|---|
| Pages はリポジトリ名のサブパス (`/merge_puzzle/`) で配信される。既定のビルドはルート配信前提なのでアセットを取りに行けず**真っ白な画面**になる | `--base-href "/merge_puzzle/"` を付ける。ワークフローではリポジトリ名から自動で組み立てている |
| CanvasKit（描画エンジン、約 1.5MB）が既定では Google の CDN から実行時に取得される。CDN が塞がれている環境では起動しない | `--no-web-resources-cdn` でビルドに同梱する |
| 直リンクやリロードで 404 になる | `index.html` を `404.html` に複製する |
| Service Worker が古い版をキャッシュし、更新が反映されないことがある | 利用者側でハードリロード。頻発するなら `--pwa-strategy=none` を検討 |

いずれもワークフロー側で対処済み。ローカルでサブパス配信・CDN 遮断の条件を再現して、起動することを確認している。

なお、日本語とラテン文字のフォントは実行時に Google Fonts から取得される。表示はされるが、
外部依存を完全に断ちたい場合はフォントをアセットとして同梱する必要がある（CJK は容量が大きい）。

## 敵の姿

守り 3〜8 に1体ずつ、姿を持たせてある。

| 守り | 敵 | | 守り | 敵 |
|---|---|---|---|---|
| 3 | 小鬼 | | 6 | 石像 |
| 4 | 骸 | | 7 | 獣 |
| 5 | 影 | | 8 | 竜 |

**ラスター画像ではなく `CustomPainter` で描いている。** 盤面のマスは実機で 40〜50px しか
なく、画像を置いても潰れて読めない。ベクターなら解像度に追従し、アセット重量も増えず
（web ビルドは CanvasKit だけで既に 1.5MB ある）、色を `Palette.wardColorFor` から取れる
ので盤面の封印と必ず揃う。

姿は**盤面の敵マスと決着画面の両方**に出る。制圧画面には討ち果たした敵、陥落・全滅画面
には討ち漏らした敵——つまり反撃してきた相手——が並ぶ。守りが厚い敵ほど枠を使い切るように
描いてあるので、同じ大きさの枠に並べると格の差が姿でも出る。

### 盤面のマスに入れるためにやったこと

マスは狭く、六角の封印・守りの数字・体力の粒で既に埋まっていた。姿と数字を同じ場所に
重ねると、どちらも読めなくなる。試した4案のうち、**姿を封印いっぱいに入れ、守りの数字を
左上の小さなチップに出す**案を採った。

| 案 | 結果 |
|---|---|
| 姿を封印の背後に透かす | 姿が数字の陰でただのノイズになる。形が読めない |
| 姿をマス全体に大きく敷く | 姿がマスからはみ出し、隣のマスと繋がって見える |
| 姿を封印の中に、数字を封印の下端に重ねる | 守り 7・8 は数字が明るい体の上に乗って読めない |
| **姿を封印の中に、数字は左上のチップ** | 姿も数字も潰れない。採用 |

数字は鎖の長さを決める唯一の値なので、姿より先に読めないといけない。チップの中を暗く
塗ってあるのは、下のマナの色（暖色にも寒色にもなる）から必ず浮かせるため。封印の内側に
あった環は、姿とぶつかるので外した。

座標は `tools/foe/shapes.py` が唯一の定義で、`lib/ui/foe_art.dart` はそこからの生成物。
Pillow で描くプレビューと Flutter の Canvas という別々の実装が同じ座標を読むので、
見た目がずれない。直し方は `tools/foe/README.md` にある。

### 魔導士の姿

![10人](tools/mage/sheet.png)

魔導士は一文字の印（焔・氷・電…）で出していた。印は名簿の札では名前と並ぶので
読めるが、**一党の帯（21px の丸）では誰なのか分からない**。10人に増えて、同じ相の
魔導士が3人並ぶようになってからは特にそうだった。

敵と同じ仕組みで姿を持たせた。`tools/mage/shapes.py` → `lib/ui/mage_art.dart`。
ラスター画像ではなくベクターなのも同じ理由で、20〜40px に縮むところに画像を置いても
潰れて読めない。

**人は描かない。** 20px の丸に人の形を入れても、誰だか分からない点の集まりにしか
ならない。描くのは**その魔導士の力そのもの**で、炎・滴・稲妻のように輪郭だけで意味が
分かる形に寄せてある。

相ごとに形の系統を揃えたので、**姿だけで相が読める**。熱は炎と渦、冷は滴と六花、
雷は稲妻と盾。色（`Palette.mageColor`）も相の色なので、誰を入れると盤面が何色に
なるかが編成の画面で二重に読める。

格の差は塗りで出した。**従者は輪郭だけ、招ける魔導士は塗り潰し。** 敵が「守りが厚い
ほど枠を使い切る」のと同じ考え方で、同じ相の3人（熱の従者・焔・烈火）が並んでも
格の順が形で分かる。

印（`Mage.sigil`）は姿に置き換わったので消した。

### 相も漢字を出さない

同じ理由で、相を示していた「熱」「冷」「雷」の漢字も消した。盤面の相の割合
（`game_screen.dart`）と編成の枠・盤面の相の帯（`home_screen.dart`）の3箇所で、
**盤面のマスと同じ色の小片**（`PhaseSwatch`）に置き換えてある。

呼び名を読んでから盤面でその色を探す、という一手間が要らない。角の丸みも
グラデーションもマスと揃えてあるので、どのマスのことなのかが説明なしに伝わる。
相が増えても呼び名を考えずに済む。

`Phase.label` は残してある。魔導士の能力の説明文（「熱を3枚以上継いだ鎖は…」）
は文なので、そこでは呼び名が要る。
